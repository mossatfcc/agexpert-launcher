# Maintaining the launcher toolkit

Repository: `C:\AgExpert\agexpert-launcher`

## Naming convention

Every skill shipped by this toolkit is prefixed `agexpert-launcher-`, so its origin is obvious
in a long, shared skill list. A new skill goes in `copilot/skills/agexpert-launcher-<verb>/`,
its `name:` frontmatter matches the folder exactly, and it is added to both the agent's skill
table and the `Copilot assets` test in `tests/Syntax.Tests.ps1`.

The installer removes previously installed `agexpert-*` skills that no longer exist in the
repository, so renames do not leave orphans behind in `~/.copilot/skills`.

## Golden rule

`config/apis.json` is the single source of truth. The PowerShell module and the VS Code
extension both read it. Never hardcode an API in either one — that duplication is what
previously let the Field API path drift out of date.

## Add or change an API

1. Edit `config/apis.json`:

   ```json
   { "name": "elmers", "proxyName": "Elmers API", "port": 44366,
     "directory": "AgExpert.Elmers/src/AgExpert.Elmers.Api", "defaultProfile": "Test" }
   ```

   | Field | Notes |
   |---|---|
   | `name` | camelCase; what the user types. Must be unique |
   | `proxyName` | Display name shown by `agexpert proxy status` |
   | `port` | Must be unique across the registry |
   | `directory` | Forward slashes, relative to the FMPro repo root |
   | `defaultProfile` | Must exist in that project's `launchSettings.json` |
   | `proxyOnly` | `true` when no local project exists; omit `directory` |

2. Validate — this checks parity, unique ports, directories, and profiles:

   ```powershell
   Invoke-Pester C:\AgExpert\agexpert-launcher\tests
   ```

3. Confirm the runtime view:

   ```powershell
   Test-AgExpertEnvironment -Api elmers
   ```

No module or extension code changes are required for a new API.

## Change launcher behaviour

| Change | File |
|---|---|
| New cmdlet the user runs | `src/module/AgExpert.Launcher/Public/<Verb-Noun>.ps1` |
| Internal helper | `src/module/AgExpert.Launcher/Private/<Verb-Noun>.ps1` |
| Terminal tab creation in VS Code | `src/extension/extension.js` |
| Command routing | `Public/Invoke-AgExpert.ps1` |

Public files are exported automatically by file name, but also add the function to
`FunctionsToExport` in `AgExpert.Launcher.psd1` so the manifest stays explicit.

Behaviour changes must land in the module or extension **and** gain a test. If you find
yourself running the same verification twice by hand, it belongs in `tests/`.

## Release

```powershell
cd C:\AgExpert\agexpert-launcher
./tools/Build-AgExpertRelease.ps1 -BumpPatch -Install    # or -BumpMinor / -BumpMajor
```

The script runs the analyzer and tests, syncs `config/` into the extension, bumps both the
module manifest and extension `package.json`, and packages the `.vsix`. `-Install` then runs
`tools/install.ps1`, updating the module, extension, agent, and skills together; without it
nothing is installed. Bumping the extension version is what forces VS Code to load new code.
Afterwards open a new terminal and run **Developer: Restart Extension Host**.

Commit the version bump so the repository never falls behind an installed build.

Then update `CHANGELOG.md` under a new version heading, using Keep a Changelog sections
(`Added`, `Changed`, `Fixed`).

## Verify a release

```powershell
pwsh -NoProfile -Command "Import-Module AgExpert.Launcher -Force; (Get-Module AgExpert.Launcher).Version"
code --list-extensions --show-versions | Select-String agexpert
```

Always verify in `pwsh -NoProfile`. A normal shell may hold stale dot-sourced functions that
mask real failures.

## Deploy to another machine

```powershell
git clone <repo> C:\AgExpert\agexpert-launcher
cd C:\AgExpert\agexpert-launcher
./tools/install.ps1 -RepoRoot <path to FMPro> -WhatIf   # preview
./tools/install.ps1 -RepoRoot <path to FMPro>
```

Machine-specific paths live in `~/.agexpert/launcher.settings.json`, which is generated by the
installer and never committed.
